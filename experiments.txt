## Experiment A

**From a tool's name and a one-line description of what it does, can the model predict which arguments the tool takes and the grammar for writing them?**

**What we did**
- **Commands:** six real ones: `find`, `grep`, `tar`, `curl`, `git log`, `jq`.
- **Names:** the real name (`grep`), a descriptive one (`search_text`, `find_files`, `http_request`, `json_query`), or a random word new for every probe (`kilafugabib`).
- **Flags:** the real ones (`-i`, `-c`, `-A 2`), or invented spellings never shown to the model (`--nocase`, `--tally`, `--trail 2`).
- **The tool:** one tool, `run {command: string}`, described as "Runs one command line and returns its output. These are the only commands available:", with one line per command, e.g. `- kilafugabib: search files for lines matching a pattern and print them`.
- **The request:** never names the command or its flags. Example: "Show each line of /srv/api/error.log matching "failed" with 2 lines before it and 6 lines after it."
- **Scoring:** the first `command` string only, by an exact parser. 400 probes per condition.

**Results**

| Name, flags | First call correct | Example call |
|---|---|---|
| real, real | 81.8% | `grep -B 2 -A 6 'failed' /srv/api/error.log` |
| random, real | 31.5% | `rilolilebot -A 6 -B 2 'failed' /srv/api/error.log` |
| descriptive, real | 9.3% | `search_text pattern="failed" path="/srv/api/error.log" context_before=2 context_after=6` |
| any name, invented | 0–0.3% | real flags were still written in 94% of real-name calls |

**What it tells us**
- **The name brings the grammar.** With the same one-line description, the real name gets the arguments right 50 points more often than a random name.
- **What that's worth:** in tokens, about 160–200 tokens of description per command (measured in B). In errors, it avoids about 2 of every 3 failures a random name makes. In a conversation (the first-round multi-turn run), opaque names took about 2.5× the turns and input tokens.
- **A readable but unfamiliar name moves the model to a different grammar.** It wrote `key=value` arguments instead of flags.

**Three biggest threats**
1. **The setup suggests a shell.** The tool name `run`, the words "command line" and the `command` field say "write Unix" before the model reads any name. That raises every real-flag number. A neutral tool and plain-text answers are being tested now.
2. **The description and the request give the command away.** "Search files for lines matching a pattern", plus "2 lines before, 6 after", describes grep. So the random-name result is recall from context, not from nothing.
3. **Scoring was strict.** Calls that do what was asked but add an unrequested option counted as wrong, for example `curl -X POST -d …`, where curl already posts. Rescoring by what each call does is running now.

## Experiment B

**What is a familiar command's pretrained grammar worth in description tokens, and how accurate is it from the name alone?**

**What we did**
- **Same as A:** the six commands, the `run {command}` tool and the kind of request. Real flags only. Real name, or a new random word.
- **Five description sizes per command**, measured in the provider's tokens:

  | Size | What it adds |
  |---|---|
  | ~3 | the name only: `- kilafugabib` |
  | ~56 | a paragraph on what it does |
  | ~145 | `Usage: kilafugabib [OPTIONS] PATTERN FILE...` and how options combine |
  | ~374 | the flag list: `-i, --ignore-case`, `-A NUM, --after-context NUM`, … |
  | ~698 | more options, notes, two worked examples |

- **Scoring:** the first call, exact parser, about 300 probes per name per size.

**Results**

| Size | Real name | Random name |
|---|---|---|
| ~3 (name only) | 81.3% | 5.7% |
| ~56 | 86.0% | 25.7% |
| ~145 | 80.7% | 79.7% |
| ~374 | 85.3% | 92.7% |
| ~698 | 89.3% | 94.0% |

**What it tells us**
- **From the name alone, the model knows the grammar about 81% of the time.** A random name alone almost never manages it.
- **A usage line is what lets an unfamiliar name catch up,** at about 145 tokens. The flag list isn't needed.
- **The name is worth about 160–200 tokens of description per command** at an 80–85% target.
- **With full description the two are about equal.** The real name's remaining misses are options nobody asked for: `grep -i` 36 times, `git log --all` 21, `curl -X POST` 21, a default curl header 20. About a third of those do exactly what was asked.

**Three biggest threats**
1. **The two names didn't have the same flags available.** A random name could use only the ~30 documented flags. The real name could use every flag the model knows, so it had more ways to add something unasked. The rerun now running gives both the same flags.
2. **Scoring was strict.** Calls with the same effect as the expected one counted as wrong, which pulls the real name down at large sizes. The rerun scores by effect.
3. **The sizes change content, not just length.** The jump at about 145 tokens is the usage line, so "worth 160–200 tokens" really means "worth about one usage line". Testing each piece of content alone would show which piece the name replaces.

## Experiment C

**When a familiar command's rules are changed and the changes are documented, does the familiar name make the model worse than an unfamiliar name taught the same rules?**

**What we did**
- **Same as A:** the six commands, the `run {command}` tool and single-call requests.
- **Each command had 13–18 changeable rules:**
  - a flag renamed: `-n` becomes `--numbered`;
  - argument order: grep takes the file before the pattern, `jq` the file before the filter, curl the URL first;
  - quoting: one value must be in double quotes.
- **Five doses:** 0, 1, 2 or 4 of the rules a probe uses changed, or all of them. Every probe used at least four rules.
- **The description documented the grammar in force:** a synopsis, every flag with its meaning, and each change stated, e.g. "Use `--numbered` (prefix each output line with its line number); `-n` and `--line-number` do not exist."
- **Two arms per dose:** the real name, and a random name with identical documentation. 300 probes per cell, 3,000 in all.
- **Old form:** the call used a renamed flag's real spelling, the old order or the old quoting.

**Results**

| Rules changed | Real name correct | Random name correct | Real − random | Old form, real vs random |
|---|---|---|---|---|
| 0 | 86.7% | 87.7% | −1.0 (noise) | 0% vs 0% |
| 1 | 74.3% | 84.0% | −9.7 (−16.1 to −3.2) | 11.7% vs 3.7% |
| 2 | 75.0% | 85.3% | −10.3 (−16.6 to −4.0) | 13.0% vs 2.7% |
| 4 | 73.7% | 82.7% | −9.0 (−15.5 to −2.4) | 14.7% vs 8.0% |
| all | 81.7% | 89.3% | −7.7 (−13.3 to −2.0) | 6.3% vs 3.0% |

**What it tells us**
- **A familiar interface with changed rules is worse than an unfamiliar one taught the same rules.** The model is about 10 points less accurate, because it keeps writing the old form even when told it no longer exists.
- **Documentation doesn't fully override what the name brings.** The real arm followed a renamed flag 96.3% of the time, against 99.7% for the random arm.
- **Most of it is `jq`.** With one rule changed, the real name was right 16% of the time and the random name 64%; the model kept the filter first and in single quotes. Without `jq`, no difference excludes zero.
- **Multi-turn check (first round):** with recovery allowed, tasks correct stayed at 93–98%. The mismatch showed up as cost instead: 3,090 rising to 4,363 tokens per correct task, above a novel grammar's 3,873.

**Three biggest threats**
1. **One command carries the effect.** `jq`'s filter syntax may be a special case: a strong habit, or harder documentation. So "almost-familiar is worse" is shown for `jq` and suggested for the others.
2. **The two arms didn't have the same flags available, as in B.** The real arm can add unrequested real flags from unchanged rules, and strict scoring counts them against it. Part of the gap may be that, not the changed rules.
3. **Single calls only.** In use, the model sees the error and recovers. The multi-turn check suggests the real price is extra tokens, not lost tasks.

## Experiment D

**If an interface looks like a familiar language but supports only part of it, does the model write the parts it doesn't support?**

**What we did**
- **One language, spelled two ways, with the same parser, syntax tree and interpreter:**
  - **restricted JavaScript:** `let`/`const`, named functions, `if`/`else`, `while`, `for…of`, `+`, list literals, `.push`, `.length`, indexing;
  - **a relabelled version of the same grammar:** `keep x := 0`, `routine f[a] begin … end`, `each x within xs begin … end`, `«strings»`, `user's name`, `xs's push[v]`.
- **The tool:** `run_program`, with a line-for-line matching grammar reference, three host functions (`getUsers`, `getOrders`, `print`) and the same example program in each spelling. Neither version was called JavaScript.
- **Restriction stated or not:** each version ran with and without a plain-words "not supported" list (arrow functions, templates, JSON, list methods other than push, …).
- **Tasks:** 38, each one full JavaScript would do with a missing construct: filter, map, join, sort, count by group, find the largest. All are doable in the subset.
- **Scoring:** the first program was run and its output compared line by line. 400 probes per arm. A detector named every JavaScript construct in programs that failed to parse.

**Results**

| Arm | Borrowed JavaScript constructs per 100 programs |
|---|---|
| JavaScript-looking, restriction not stated | 13.5 |
| JavaScript-looking, restriction stated | 0.0 |
| relabelled, not stated | 0.8 |
| relabelled, stated | 1.8 |

**What it tells us**
- **Looking like JavaScript draws JavaScript:** 5.4× the borrowed constructs (interval 3.0–12.8). All 50 syntax errors in the JavaScript-looking version were valid JavaScript.
- **One sentence switches it off.** Stating what isn't supported cut borrowing to 0 of 400 programs and raised programs correct by 12 points.
- **It's narrow.** The counting `for (let i = 0; …)` loop is 39 of the 54 borrowings. No arrow functions, template literals or JSON appeared at all.
- **Multi-turn check (first round):** with the restriction unstated, all 35 incorrect calls were valid shell or JavaScript, mostly shell globs. Stating the restriction cut trials with an unsupported construct from 36% to 4% in shell and from 24% to 0% in JavaScript.

**Three biggest threats**
1. **The result rests on one construct.** Without the counting loop the ratio is 1.5×, which isn't settled. That loop is arguably the most natural loop in any C-family language, not something specific to JavaScript.
2. **The scorer was changed after the data was seen.** "Relabelled errors are mostly invented" passes only after a fix (an apostrophe inside a name now counts as a misspelling). Before the fix it was 59%, not settled.
3. **The detection isn't symmetric.** The JavaScript-looking arm was checked by a full JavaScript parser; the relabelled arm by scanning for JavaScript spellings. The two arms' borrowing counts may not be measured the same way.

## Experiment E

**Can the model learn a grammar it has never seen from documentation, from examples, or both, and does it matter where the example appears?**

**What we did**
- **An invented syntax for a library desk:** `^return^ member~m-12 / books~b-7&b-9 ?? condition~worn / !waive ^^`.
  - `^op^` picks the operation; required arguments come first, separated by ` / `.
  - Optional arguments come after ` ?? `; lists use `&`; text with spaces goes in `< >`; a switch is `!name`; the line ends with ` ^^`.
- **Six operations** (find, borrow, return, reserve, loans, renew), through one tool, `submit {line}`.
- **Every condition got the same vocabulary:** each operation's and parameter's name and meaning.
- **What changed was how the syntax was taught:**
  - nothing;
  - a formal grammar of about 250 tokens;
  - one example (a `borrow` call);
  - two examples (adding a `reserve` call with a switch);
  - the grammar plus one example.
- **Where the example sat:** in the tool definition, or just before the request, as an earlier accepted exchange ending `accepted: <line>`.
- **Probes:**
  - 400 per condition asking for operations no example shows: find, return, loans, renew;
  - 100 asking for `borrow` with new values;
  - 200 with a second, plain-JSON tool alongside.
- **Scoring:** the first call, by an exact parser.

**Results**

| Teaching | Example in the definition | Example just before use |
|---|---|---|
| nothing | 0.0% | – |
| grammar only | 78.0% | – |
| one example | 38.0% | 37.5% |
| two examples | 63.0% | 64.3% |
| grammar + one example | 90.8% | 95.3% |

First call correct on operations no example shows, n = 400 per cell.

**What it tells us**
- **An example teaches exactly what it shows.** Copying the shown operation with new values was 100% correct. Parts the example didn't contain were never learned from it: 0 of 185 probes needing the switch, 0 of 85 needing `< >` text.
- **The grammar does most of the work, and grammar plus one example works best:** 95.3%.
- **Placement matters only when the example comes with its grammar:** +4.5 points (1.0–8.2). For an example alone, placement made no difference.
- **Without teaching, the model falls back on familiar grammars:** all 400 calls were shell-style words (308) or `key=value` (92). With any teaching, wrong calls stayed inside the invented syntax and broke its rules.
- **No mix-ups between tools:** 0 of 400 calls sent the invented syntax to the JSON tool, or JSON to `submit`.
- **Multi-turn check (first round, a second invented grammar):** documentation alone was enough (149 of 150 first calls). An example returned as the result of the model's own failed call worked far better than the same example in the definition: next call correct 83% against 33%.

**Three biggest threats**
1. **"Just before use" was an earlier successful exchange, not feedback on the model's own failed call.** The multi-turn check suggests feedback is what makes placement matter, so the placement verdict depends on that choice.
2. **One invented grammar, with spacing rules.** The parser enforced the grammar's spaces; relaxing them lifts grammar-only from 78% to 88%. A different invented grammar could shift every number.
3. **The examples were chosen to leave features out.** The 0 of 185 for the switch is close to true by construction. It shows examples don't teach what they omit, not how well examples teach in general.

## Experiment F

**When a call fails and the agent retries, how much does that error cost in tokens and dollars, and does it depend on when the error happens and how large the tool definitions are?**

**What we did**
- **An issue tracker as files under `/tracker`:** 90 issues, 14 components, 24 users, 6 teams. It's reached through one tool, `run {command}`, with six read-only Unix commands (`ls`, `cat`, `grep`, `head`, `wc`, `find`).
- **Tasks are chains:** each step needs the previous answer, 4–6 calls in all. Example: "ISS-116 is blocked by another issue. Which team owns that blocking issue's component?"
- **Two definition sizes:** about 940 tokens, or about 8,900 (a long manual plus 34 tools the tasks never use).
- **Part 1, replay with no model behaviour:**
  - 30 recorded successful conversations had one incorrect call, its error and the correct call inserted early, in the middle, or late;
  - each was sent to the provider exactly as an agent loop would send it: 720 replays, 4,572 requests;
  - billed cost and cached tokens came from the provider's own usage.
- **Part 2, live:** 240 runs. One call at the first, middle or last expected position was answered "the command did not run. Run the same command again", against runs with no injected error.

**Results**

| Measure | Small definitions | Large definitions |
|---|---|---|
| input that came back cached | 99.8% | 99.8% |
| extra input tokens from one error (live) | about 1,400–1,500 | about 10,000 |
| share of the error's cost removed by caching | 78–90% | 86–88% |
| early − late error, billed (replay) | +1.2 µ$ (−0.9 to 5.1) | −0.8 µ$ (−0.9 to −0.6) |

The model repeated the failed call in 144 of 144 live runs; each error cost exactly one extra turn.

**What it tells us**
- **One error costs one extra turn, and that turn costs what it resends:** the definitions plus the conversation so far. Large definitions make each error cost about 7× more tokens.
- **Early errors don't cost more than late ones.** Nothing carries an error forward; what the extra turn resends is largest late.
- **Caching removes most of the dollar cost.** The provider served nearly every repeated token from cache, at about a tenth of the price. N × S holds for tokens sent, not for dollars.
- **First-round check (Experiment 6):** the same result. History grows input faster than linearly, and an error at the first call cost 137 tokens against 2,070 for a late one on small definitions.

**Three biggest threats**
1. **Caching depends on the provider:** prefix caching above 1,024 tokens, at a tenth of the price. With another provider or pricing, the dollar result could reverse.
2. **The conversations were short,** 5–6 turns. In long agent sessions, where history dominates, position effects might look different.
3. **The injected error was artificial.** "Run the same command again" always costs exactly one turn. Real grammar errors need reasoning and can repeat: after a bare error in Experiment 9, the model repeated its mistake about 5 times.

## Experiment G

**When an interface's grammar doesn't match what the model expects, do the attempts allowed and the quality of the error message decide whether that mismatch costs a task or only tokens?**

**What we did**
- **The issue tracker and `run {command}` tool from F, with three rules changed:**
  - paths start with `@` (`@issues/ISS-101`);
  - options start with `+` (`+r`, `+l`, `+n 5`);
  - grep takes its paths first (`grep +r +l @issues "status: open"`).

  The changes were documented by usage lines only, with no examples.
- **Tasks:** four independent questions, each answerable with one call. Example: "How many issues are assigned to zali?"
- **2 × 2 design:**
  - attempts: one try plus one fix (2 tool turns), or up to 12 turns;
  - feedback: `ERROR: invalid command`, or the error plus the usage line and one correct example.
- **A control:** the unchanged familiar interface. 120 tasks per cell, 600 runs.

**Results**

| Condition | Tasks correct | Tokens per correct task |
|---|---|---|
| one try + fix, bare error | 90.0% | 4,299 |
| one try + fix, helpful error | 96.7% | 4,251 |
| many turns, bare error | 96.7% | 4,274 |
| many turns, helpful error | 96.7% | 4,297 |
| unchanged familiar interface | 96.7% | 3,726 |

**What it tells us**
- **A bare error with one try loses tasks:** −6.7 points (−13.6 to −0.2). A helpful error, or more turns, recovers them all.
- **With recovery, a mismatched grammar costs about 15% more tokens per correct task** than the familiar interface (+571, 258–889), and no tasks.
- **Most incorrect calls were the new grammar written slightly wrong,** e.g. a pattern left unquoted, not the old Unix form.
- **First-round checks:**
  - Experiment 2: after an incorrect call, one try plus one fix finished 19% of tasks, many turns 87%.
  - Experiment 9: a bare error made the model repeat its mistake about 5 times, at three to four times the cost.

**Three biggest threats**
1. **Ceiling.** Four independent lookups are easy: 90–97% everywhere. Small effects can't separate, which is why the result is significant only with bare errors.
2. **"One try" wasn't really one try.** Parallel calls were allowed, so two tool turns could carry many calls and fix several errors at once.
3. **The scorer was changed after the data was seen.** Ignoring invisible characters inside names flipped 2 runs. The bare-error verdict is unchanged, but the pooled result moved from just significant to not settled.

## Experiment H

**When a task needs a chain of dependent lookups, does letting the model write one program instead of calling tools one at a time save more as the chain gets longer?**

**What we did**
- **A generated world of 715 linked records:** people, teams, offices, cities, countries, projects.
  - Ids are opaque; a record holds only the ids it links to, so one `get` is exactly one hop.
  - Tools: `get(id)`, `find(type, field, value)` returning ids, and `list(type, page)` with 10 per page.
- **Four task shapes at depths 1, 2, 4, 8 and 12,** 100 tasks in all:
  - **chain:** each lookup needs the previous one's id;
  - **fan-out:** D independent lookups, then aggregate;
  - **filter:** check each of D items with a second lookup;
  - **branch:** the next hop depends on a value just read.

  A separate solver reproduced every answer through the tools alone.
- **Three interfaces with the same turn budget,** 2·D + 6:
  - one call per turn: extra calls were answered "did not run";
  - parallel calls;
  - JavaScript: one `script {source}` tool running real JavaScript with the tools bound.
- **Runs:** 5 per task per interface, 1,500 in all.

**Results**

| Depth | Best structured − JavaScript, tokens per correct task |
|---|---|
| 1 | 255 (100–373) |
| 2 | 595 (472–710) |
| 4 | 998 (706–1,255) |
| 8 | 2,423 (1,655–3,179) |
| 12 | 6,668 (5,524–7,733) |

Tasks correct were 94–100% for every interface at every depth.

**What it tells us**
- **A program is cheaper at every depth, and the saving grows with depth.** Every step from one depth to the next is above zero, in billed dollars too.
- **It saves cost, not tasks:** accuracy was the same everywhere.
- **The model under-uses the script.** It wrote one program for the whole task in only 380 of 500 runs, and otherwise stepped through chains one lookup per script.
- **First-round check (Experiment 7):** one sentence saying "one program can do every step" cut JavaScript's cost on deep chains by 63%, with 90 of 90 correct. Python's first program usually reached for Python's own `open()`, which fails there.

**Three biggest threats**
1. **The world is as favorable to scripting as it gets.** Every step is a mechanical lookup with no judgement. Real tasks that need reading and deciding at each step may not compose.
2. **The size of the saving depends on the prompt.** The model composed only when it saw the dependency up front, or when told it could. The measured saving is a lower bound that moves with instructions.
3. **One-call-per-turn was enforced, unlike real APIs.** The parallel arm covers part of that, but a structured API with a batch call wasn't tested.

## Experiment 0 (first round)

**Of the incorrect tool calls our earlier runs kept, how many were constructs borrowed from the language the interface resembles?**

**What we did**
- **No model calls.** We classified 312 incorrect calls kept from earlier runs:
  - 254 of 5,138 calls in the tool-dialect runs (the same tools written as JSON fields or as command lines);
  - 58 of 179 calls to our scripting tool, ToolScript, from before and after it became real JavaScript.
- **Each was classed by rule as:** documented syntax used wrongly, supported familiar syntax, unsupported familiar syntax, or no recognizable source. 40 were checked by hand.

**Results**

| Interface | Syntax failures | Valid in the familiar language, unsupported here |
|---|---|---|
| ToolScript, nearly JavaScript | 44 | 89% |
| command-line versions | 74 | 23% |

**What it tells us**
- **Nearly-JavaScript failed on real JavaScript:** arrow functions 18, template literals 11.
- **Command lines failed mostly where two grammars nested.** SQL quoted inside shell quotes (28 of 39) is invalid in both: grammar collision, not borrowing.
- **No pipes:** none of 2,194 command-line calls used a pipe, redirect or `&&`.

**Three biggest threats**
1. **The classification rules are ours.** A different reasonable rule set could shift the shares.
2. **One judgement call decides the command-line number.** Counting 14 double-quoted SQL strings as invalid SQL instead of borrowed drops 23% to 4%.
3. **The calls aren't independent.** Three scenarios hold most of the ToolScript failures, so the intervals are too narrow.

## Experiment 8 (first round)

**What makes an agent's interface expensive: the size of the tool definitions, the length of each call, or whether calls can be combined into one program?**

**What we did**
- **The package-registry world and 15 tasks, in a 2 × 2 × 2 design:**
  - call length: short or long tool and argument names;
  - composition: one call per turn, or a JavaScript script;
  - definition size: the five tools, or the same plus 30 unused tools.
- **Runs:** 45 per cell, 360 in all, with every token split into repeated definition, history, results and call text.

**Results**

| Factor | Effect on tokens per correct task | Effect on billed input |
|---|---|---|
| definition size | ×2.90 (+5,133, interval 4,136–6,164) | ×0.73: cheaper, because 90% was cached |
| composition | within noise | within noise |
| call length | within noise | within noise |

**What it tells us**
- **Definition size dominates the tokens sent.** Call text was 2–10% of input in every cell.
- **Caching flips the dollars.** The large definition was cheaper to bill, because it crossed the provider's caching threshold.

**Three biggest threats**
1. **Short tasks, about 3 turns,** so composition had little to save (Experiment H shows it saving at depth).
2. **The long-name variant also lengthened the definitions,** so call length is partly a definition-size effect.
3. **The billing result depends on one provider's caching threshold and price.**
