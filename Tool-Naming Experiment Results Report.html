Tool-Naming Experiment: Results Report

This report explains an experiment testing how an AI model's ability to use tools depends on what those tools are named, and on how the model is allowed to call them. It's written in two parts:

  • Overview — a plain-language summary of what was tested and what we found, written for readers interested in AI who may not know all the jargon.
  • Methodology — exactly how the test world, naming conditions, interfaces, and tasks were built.
  • Detailed Results — full data tables (success rates, error-tag breakdowns, per-tier breakdowns).
  • Caveats and Next Steps — how much weight to put on these results, and what to test next.

Overview

Note on data correction: After the initial version of this report was written, a scoring bug was found and fixed (see Methodology for details). This version reflects the corrected results. The bug caused the model's genuinely correct answers to short free-text questions (e.g. "What license does pkg-113 use?") to be marked wrong when phrased as a full sentence ("pkg-113 uses the GPL-3.0 license.") instead of the bare value ("GPL-3.0"). Fixing this raised overall success from 48.5% to 64.5% and changed none of the directional findings below — if anything, it makes the central pattern clearer.

What this experiment was about

Modern AI assistants (like Claude or GPT models) often don't just answer questions directly — they're given a set of "tools" they can call to look things up, similar to how a person might use ls, grep, or cat commands in a Unix terminal to browse files. The AI reads a short "manual" describing each tool, then decides which tool to call, with what arguments, to answer a question.

A natural question for anyone building these systems is: does it matter what you name the tools?

If you give a tool a name the AI has seen a million times during its training (like grep for "search text") versus a name it's never seen before (like qovrex), does that change how well it uses the tool — even if the tool manual explains exactly what the tool does either way?

This experiment tested that question, and paired it with a second question: does the naming effect depend on how the AI is allowed to call tools — one at a time in a back-and-forth conversation, versus writing a whole script up front, versus typing a Unix-style command line?

How the test worked (in plain terms)

We built a small fake "world" — a dependency graph loosely modeled on a software package manager (think: npm or pip), with 40 fictional "projects" that depend on some of 150 fictional "packages," including realistic messiness like circular dependencies and version conflicts. This fake world lives entirely in a file the AI never sees directly — it can only learn about it by calling tools.

We gave the AI 24 questions about this world, split into three difficulty levels:

  • Tier 1 (easy): simple lookups, e.g., "what license does package X use?"
  • Tier 2 (medium): lookups that require searching/counting across many things, e.g., "how many projects depend on package Y?"
  • Tier 3 (hard): questions that require combining two separate lookups, e.g., "which projects depend on any MIT-licensed package?" (first you must figure out which packages are MIT-licensed, then cross-reference that against every project's dependency list.)

We tested three naming conditions — three different sets of names for the same five underlying tools:

  • Condition A ("A-full"): tools are named exactly like real Unix commands — ls, grep, find, cat, wc — names the AI has almost certainly seen thousands of times during training.
  • Condition B: tools are given sensible, descriptive but non-standard names — list_entries, search_content, find_by_pattern, read_record, count_matches — names a human would understand immediately, but that don't match any specific well-known tool.
  • Condition C: tools are given random, made-up names — pronounceable but meaningless, with no hint about what they do from the name alone.

Crucially, in every condition the AI is given a full, accurate manual explaining what each tool does — so if naming doesn't matter, performance should be roughly equal across A/B/C. If naming does matter — perhaps because familiar names let the model lean on things it already "knows" from training, beyond what's written in the manual — we'd expect to see differences.

We also tested three interface styles — three different ways the AI is allowed to call these tools:

  • Sequential (tool-calling): the AI calls one tool, sees the result, calls another, back and forth — like a normal conversation — up to several turns.
  • Scripted: the AI writes one Python-like script in a single shot that calls the tools in sequence, with one chance to fix it if it errors.
  • Shell: the AI writes one Unix-style command line in a single shot (optionally piping output from one tool into another, like ls | grep foo | wc), with one chance to fix it if it errors.

Crossing 3 naming conditions × 3 interfaces × 24 tasks × 3 repeated trials gave us 648 total AI "attempts," each scored automatically as correct or incorrect against a known right answer.

The headline finding

Naming barely matters for two of the three interfaces — but it matters a lot for the Unix-shell-style interface.

  • In the sequential (back-and-forth) and scripted (write-a-script) interfaces, success rates were only mildly affected by naming, and if anything slightly favored less-familiar names (a small, likely-noise-driven effect, not a meaningful disadvantage).
  • In the shell (type-a-command-line) interface, success dropped sharply and consistently as names became less familiar: 61.1% success with real Unix names → 45.8% with sensible names → 41.7% with random names.

In other words: giving a tool a familiar name only seems to help when it's also being used in a familiar way. Typing ls | grep foo | wc works well because the AI has seen that exact pattern countless times — the name and the "grammar" (how you combine commands with pipes) are both familiar together. But calling a function named list_entries(...) doesn't get a special boost just from having a human-readable name, because there's no deep well of "function-calling muscle memory" the same way there is for Unix command-line idioms.

When we dug into why performance dropped under unfamiliar shell names, the answer was clear: the AI simply guessed the wrong command names or mangled the pipe syntax far more often (25 and 24 such mistakes out of 72 attempts for the sensible- and random-name conditions, versus only 5 for real Unix names) — not that it misunderstood the task itself.

A second, independent finding: the hardest "Tier 3" questions (the ones requiring two combined lookups) were difficult everywhere, but especially so for the shell interface, which simply cannot express a two-step combined lookup in its simplified command grammar — regardless of naming, performance for these tasks flatlined around 12.5% in the shell interface, while Tier 1 and Tier 2 questions in the shell interface still showed the full naming-driven decline described above. This is a structural limitation of what counts as "a single shell command" in this test, not something naming can fix.

Why this matters

This result lines up with a specific hypothesis: it's not naming alone that creates a training-familiarity advantage — it's naming combined with a familiar way of composing calls together. If you're designing tool-use interfaces for AI agents, the practical takeaway is that tool names probably matter most when paired with syntax/calling-conventions the model already deeply knows (like Unix pipes), and matter much less when the calling convention itself is already novel to the model (like a bespoke function-calling API) — in which case the manual you give it seems to do most of the work regardless of what you name things.

Methodology

The test world

A synthetic dependency graph was generated deterministically (fixed random seed 42): 40 fictional software "projects," each depending on some subset of 150 fictional "packages." The generator deliberately injects realistic messiness: 2 forced circular dependencies and 3 forced version conflicts, so that some tasks require handling edge cases rather than a perfectly clean tree.

This graph is exposed to the AI model only through a virtual file system layer, which maps it onto Unix-like paths — e.g. /projects/<name>/deps.txt (a text file listing a project's dependencies) and /packages/<name>/meta.json (a JSON file with package metadata like license and version). The model never sees the underlying graph data structure directly; it can only learn about the world by calling tools (or typing shell commands) that read from this virtual file system.

The five shared tools ("primitives")

Regardless of naming condition, there are exactly five underlying capabilities available, each behaving identically across all conditions — only the name shown to the model changes:

Logical ID Behavior (same in every condition) "A-full" name (real Unix) "B" name (descriptive)
P1 List entries in a directory ls list_entries
P2 Find files by name pattern find find_by_pattern
P3 Search file contents by pattern grep search_content
P4 Read a file's full contents cat read_record
P5 Count matching lines wc count_matches

Condition C ("random names") uses pronounceable but semantically meaningless names, generated with a fixed random seed and length-matched to the Condition B names, so that condition C differs from B primarily in familiarity, not in surface length or structure.

In every condition, the model is given a complete, accurate manual (a short description of each tool, its arguments, and what it returns) before being asked any task — so any performance difference between conditions reflects something beyond what's written down, presumably prior training exposure to the name itself.

The three interface styles ("harnesses")

  1. Sequential — a standard multi-turn tool-calling loop (similar to typical "agentic" AI assistants). The model calls one tool, receives the result as a new message, and can call another tool or give a final answer, for up to 15 turns (raised from an initial cap of 8 — see "Known issues identified and fixed" below).
  2. Scripted — the model writes a single Python-like script in one shot, calling the five tools as if they were ordinary functions (e.g., list_entries("/projects")). The script runs in a restricted sandbox (no file/network access, no eval/exec, limited builtins). If the script errors, the model gets exactly one repair attempt before the trial is scored as failed.
  3. Shell — the model writes a single Unix-style command line in one shot (e.g., find /packages "*/meta.json" | grep MIT | wc), executed by a simplified pipeline interpreter that supports exactly one "source" command optionally piped through one or more filter/count stages. Like the scripted interface, there is exactly one repair attempt if the first command errors.

Both scripted and shell are deliberately "single-shot" (one attempt + one repair) specifically so they can be compared against each other on equal footing — this isolates whether familiar Unix-pipe grammar (shell) provides a benefit beyond familiar naming alone (scripted), since both interfaces share the same turn structure and differ mainly in calling convention.

Tasks and difficulty tiers

24 hand-written tasks, 8 per tier:

  • Tier 1 — single-hop lookups (e.g., "What license does package X use?")
  • Tier 2 — lookups requiring search/aggregation across many items (e.g., "How many projects depend on package Y?")
  • Tier 3 — composed, multi-step lookups requiring two independent queries to be combined (e.g., "Which projects depend on at least one MIT-licensed package?" — requires first identifying all MIT-licensed packages, then cross-referencing every project's dependency list against that set).

Scoring

Each task has a ground-truth "oracle" answer computed directly from the underlying graph data (independent of the tools/VFS, to avoid circular validation). The model's free-text final answer is scored with a lenient parser that tolerates prose, reordering of list items, and extraneous words, but requires the substantive content to match exactly (e.g., a list answer must contain all correct items, not a subset). The scorer handles four answer types: list, int, bool, and str.

Scoring bug found and fixed

While reviewing the unexpectedly high overall failure rate, a bug was found in the str-type scoring path (used by 6 of the 24 tasks — short factual lookups like license, owner, and date fields). The original implementation required the model's entire response, after light normalization, to equal the oracle value exactly. This meant a genuinely correct answer phrased as a sentence — e.g. "pkg-113 uses the GPL-3.0 license." — was scored as incorrect against the oracle "GPL-3.0", purely because the full sentence doesn't equal the bare value. The other three answer types (list, int, bool) already extracted the relevant content from surrounding prose; str did not.

Fix: the str scorer now first checks for an exact normalized match (preserving prior behavior), and if that fails, searches for the oracle value as a whole-word/whole-token substring within the normalized response (e.g. "gpl-3.0 license" contains "gpl-3.0" as a bounded token, but "gpl-3.0.1" or "not-gpl-3.0ish" would not falsely match, since the search uses word boundaries). This mirrors the leniency already applied to the other three answer types.

Validation of the fix:

  • tests/test_scoring.py (5 existing scoring unit tests) continue to pass unchanged after the fix.
  • The entire existing 648-trial dataset was re-scored offline using the fixed scorer against the exact same saved model responses (no new model calls were made — the underlying str-type questions and all other data are unchanged). This produced 104 trials flipping from incorrect to correct, and zero trials flipping from correct to incorrect, confirming the fix is strictly a correction of false negatives, not a change in scoring strictness. Overall measured success rose from 48.5% to 64.5%. All results tables in this report reflect the corrected scoring.

Model and execution details

  • Model: gpt-6-luna, accessed via a custom Anthropic-Messages-API-compatible proxy ("Luna"), not a native Anthropic endpoint.
  • Experimental design: 24 tasks × 3 interfaces × 3 "core" naming conditions (A-full, B, C) × 3 repeated seeds = 648 total trials.
  • Each trial logs: tokens used (prompt + completion), number of turns/calls, wall-clock time, final answer, correctness, and (if incorrect) an error tag classifying the failure (e.g., invalid_name for calling a tool/command that doesn't exist, wrong_args for malformed arguments, primitive_error for a valid call with bad input values, timeout for exceeding the turn/attempt budget, or no tag at all for a plain wrong-answer).

Known issues identified and fixed before this run

Two genuine implementation limitations were found and corrected prior to running this experiment, both confirmed via a smaller pilot run before committing to the full 648-trial run:

  1. Sequential turn budget too tight: The original 8-turn cap was cutting off the model mid-enumeration on harder tasks. Raised to 15 turns. Confirmed fix: a Tier-3 task that previously failed under the old cap succeeded in 6 turns post-fix.
  2. Scripted sandbox blocked regex/JSON parsing entirely: The sandbox's security filter blocked any import statement, which incidentally blocked legitimate use of Python's re (regex) and json modules — tools genuinely needed for some tasks (e.g., parsing a package's metadata file to check its license field). Fixed by exposing safe, read-only facades for the handful of needed functions (re.search, re.match, re.findall, re.split, json.loads) directly in the sandbox's execution environment, without opening up broader import capability. Confirmed via a live diagnostic: a model-generated script using both json.loads(...) and re.search(...) ran successfully.

A third limitation — the shell interface's inability to express two-step "join" queries in its simplified single-pipeline grammar — was identified but deliberately not fixed, since doing so would change what "the shell interface" means for the purposes of this study (it is intended to represent a constrained, linear Unix-pipe style of composition, not an arbitrarily expressive scripting environment). This is treated as a structural property of the condition being tested, not a bug.

Key observations:

  • Tier 1 and Tier 2 (the single-hop and aggregation tasks) are now solved 80–100% of the time across sequential and scripted, consistent with these being "easy/medium" tasks for a capable model once the scoring bug is corrected.
  • The shell naming effect is now clearly visible in Tier 1 and Tier 2 specifically: Tier 1 drops 87.5% → 66.7% → 66.7%, and Tier 2 drops 83.3% → 58.3% → 45.8% as names become less familiar.
  • Shell's Tier 3 performance is flat at exactly 12.5% regardless of naming condition — unlike Tier 1/2, Tier 3 doesn't move at all with naming. This confirms the structural-limitation hypothesis: Tier 3 tasks require a two-step "join" that the shell interface's single-linear-pipeline grammar cannot express at all, so no amount of naming familiarity can rescue it — the ceiling is set by interface expressiveness, not naming.
  • Tier 3 remains the hardest tier everywhere (12.5%–62.5%), confirming these composed tasks are intrinsically harder regardless of naming or interface — sequential/scripted retain some ability to improve on Tier 3 with familiar grammar workarounds (multi-turn retries, script loops), while shell's single-shot linear-pipe grammar cannot.

Confirmation that bug fixes worked (pilot run, pre-full-run)

A smaller 27-trial pilot (3 tasks, one per tier, × 3 interfaces × 3 conditions, 1 seed) was run after applying two harness fixes described in Methodology, specifically to confirm they resolved the originally-observed Tier-3 failures before committing to the full 648-trial run:

  • sequential / A-full / Tier-3 task succeeded using 6 of the now-available 15 turns (this exact task had been failing under the original 8-turn cap).
  • A scripted Tier-3 trial's generated script was inspected directly and confirmed to use json.loads(...) to parse package metadata and re.search(...) / re.split(...) for pattern matching — both previously blocked, now working without sandbox errors.
  • The shell interface continued to fail Tier-3 tasks in the pilot (as expected, since the structural join limitation was intentionally left unaddressed) — this failure mode was separately confirmed via a live diagnostic in which the model repeatedly attempted and failed to construct a valid multi-stage pipeline for the composed query, eventually exceeding even a 60-second diagnostic timeout while retrying.

Caveats and Next Steps

Caveats — how much weight to put on these results

  • Single model, single run size. All 648 trials used one model (gpt-6-luna) accessed through a custom proxy, with 3 repeated seeds per cell. This is enough to spot a clear pattern (like the ~19-point shell naming effect, which is large, consistent across Tier 1 and Tier 2, and backed by a specific, legible mechanism — invalid_name errors) but is not a large enough sample to make statistically rigorous, publication-strength claims, especially for the smaller sequential/scripted differences (which are within noise at this sample size regardless of their direction).
  • Single-model risk. Because only one model was tested, we can't yet tell whether this is a general property of language models trained on large amounts of Unix/code data, or specific to this particular model's training mix. Testing a second, differently-trained model via the same harness would be the most valuable next step to distinguish these.
  • A scoring bug was found and fixed during analysis. The original str-type answer scoring required an exact full-response match, which incorrectly penalized correct answers phrased as sentences rather than bare values. This was caught by noticing an unexpectedly high failure rate on "easy" Tier-1 tasks and investigating individual failed trials directly. After the fix (validated by re-scoring the same saved responses with zero correct→incorrect regressions), overall success rose from 48.5% to 64.5%, and Tier 1/2 success rates now sit in the much more plausible 80–100% range. This episode is itself a useful methodological reminder: an unexpectedly high failure rate on tasks that should be easy is worth investigating as a possible harness/scoring artifact before concluding the model is the weak link.
  • Plain reasoning errors are still the largest remaining failure mode, concentrated in Tier 3. Even after the correction, roughly two-thirds of all failures (151 of 230) are plain wrong answers unrelated to any naming or syntax issue, and these are increasingly concentrated in the hardest, composed Tier-3 tasks (12.5–62.5% success) rather than spread evenly across all difficulty levels. This means remaining headroom for improvement is now more clearly a task-composition-difficulty story than a general "the model struggles with these tools" story.
  • The shell interface's Tier-3 ceiling is a scoping choice, not evidence that "shells are bad at hard tasks." The simplified shell grammar used here deliberately supports only a single linear pipeline (one source command, optionally piped through filter/count stages) and does not support command substitution or multi-step joins. A real Unix shell (with subshells, variables, and loops) could express these composed queries. The flat 12.5% Tier-3 ceiling reflects this specific simplified grammar, not a general claim about shells or Unix tooling.

Suggested next steps

  1. Increase sample size (more seeds), focused on the shell row, since that's where the effect is largest and most actionable — this would tighten confidence intervals on the A-full vs. B vs. C comparison specifically for shell, and on Tier 1/Tier 2 within it.
  2. Repeat the experiment with a second, differently-trained model via the same harness, to test whether the shell-naming effect generalizes or is specific to this model's training data.
  3. Consider a controlled variant of the shell interface that can express two-step joins (e.g., via explicit intermediate-variable support), to separate "shell grammar helps because it's familiar" from "shell grammar helps except when the task structurally doesn't fit the grammar at all" — this would cleanly separate the naming effect from the expressiveness ceiling currently conflated in the Tier-3 shell numbers.
  4. Investigate the dominant wrong-answer failure mode on Tier 3 with qualitative review of a sample of incorrect-but-well-formed responses, since this is now the largest single remaining opportunity for improving overall success rates, independent of the naming question.
  5. Audit the remaining list/int/bool scoring paths with the same scrutiny applied to str, now that one scoring-bucket bug has been found — a quick spot-check of a sample of failed trials in each answer type is cheap insurance against further scoring-artifact-inflated failure rates.
