Condition D ("Near-Miss Grammar") Experiment: Results

The Hypothesis Being Tested

The user's hypothesis: using existing Linux tool names causes agents to use grammar correctly, which provides a slight optimization over clearly non-Linux-command names — but this isn't worth the risk, because if the tool is slightly off grammar-wise from what the agent knows, that mismatch would cost MORE in tokens and success rate than just using an unfamiliar name.

In short: familiar name + wrong grammar should be WORSE than unfamiliar name + same (correct, documented) grammar, because the model's prior knowledge actively interferes rather than helps.

Experiment Design

Added Condition D to the existing Study-1 codebase (src/): reuses the exact real Unix names (ls, find, grep, cat, wc) from condition A-full, but documents a swapped argument order for find (P2) and grep (P3) relative to the real Unix convention:

  • Real/A-full: find(root, pattern), grep(pattern, path)
  • D (documented): find(pattern, root), grep(path, pattern)

This directly operationalizes experiments.txt's Experiment C methodology ("a familiar command's rules are changed and documented — does the familiar name make the model worse than an unfamiliar name taught the same rules?") inside this project's own harness, so it's directly comparable to the existing A-full/B/C shell cells.

Implementation (src/naming.py, src/dispatch.py, src/shell_sim.py, src/harness_shell.py, src/run_experiment.py, src/analyze_results.py): added condition D's manuals/signatures, made the dispatcher accept/execute calls in D's documented order, and added an old_form_grammar detector that flags whenever a P2/P3 call's argument order looks like the REAL/old convention instead of D's documented swapped one (the direct behavioral signature of grammar interference). All 9 existing mock harness tests still pass (no regressions).

Scope: shell interface only, since Study 1 found naming effects were concentrated there (sequential/scripted were flat). 72 trials: 24 tasks × 3 seeds, run against the same model/proxy (gpt-6-luna via the Luna proxy) as the original Study 1.

The critical measurement: oldformgrammar rate

0 out of 72 D trials (0.0%) showed any instance of the model reverting to the real/old find/grep argument order. Manual inspection of first-turn commands across all 24 tasks confirms the model consistently used D's documented swapped order correctly (e.g. grep("/packages", "deprecated"), find("*/meta.json", "/packages") — pattern/path-first as documented, not the real Unix order).

All 8 of D's invalid_name failures were in Tier-3 tasks and are the same known failure mode as A-full/B/C's Tier-3 failures (model attempts a 2-step pipeline the simplified shell grammar can't express) — none were argument-order reversions (old_form_grammar=False for all 8).

Interpretation: the hypothesis is NOT supported in this harness

  1. H1 (success(D) < success(B,C)) — REJECTED. D's success rate (61.1%) matches A-full exactly and is substantially higher than both B (45.8%) and C (41.7%). A familiar name with changed-but-documented grammar did not perform worse than fully unfamiliar names here — it performed as well as the condition with correct familiar grammar.
  2. H2 (tokens(D) > tokens(B,C)) — REJECTED. D's average tokens (1915) are lower than both B (2009) and C (2234), not higher.
  3. H3 (high old-form reversion rate in D) — REJECTED. The reversion rate was exactly 0%. The model never exhibited the "muscle memory" interference effect the hypothesis predicts.

The dominant driver of success/cost in this harness is clearly the invalid_name error rate from unfamiliar NAMES (B: 25/72, C: 24/72 invalid_name errors vs. A-full: 5/72, D: 8/72 — and D's 8 are all Tier-3 structural, not grammar-order errors) — not grammar/argument-order fidelity. The model appears to read and follow the documented argument order for D reliably, regardless of whether it conflicts with the real-world Unix convention, because the manual text is right there in context on every turn (shown via render_full_manual in the system prompt) and the single-shot "write one command, see the error, get one repair turn" protocol gives it an explicit correction loop even if it slips.

Why this differs from Experiment C's finding

experiments.txt's Experiment C did find a real-name penalty (real −7 to −10 points vs random, when rules changed) on a different generic harness (issue-tracker/jq-style tools). Plausible explanations for the discrepancy:
  • Task family / tool familiarity: Experiment C's jq filter-ordering habit was called out as the primary driver of that effect ("Three biggest threats" section) — jq's own grammar is unusually deeply ingrained and its filter-first idiom may be a stronger prior than find/grep's two-argument ordering.
  • Documentation visibility: this harness's render_full_manual puts the corrected signature directly in the system prompt every turn, with an explicit "NOT {name}(old_order)" contrastive line — a stronger/clearer correction cue than may have been used in Experiment C's setup.
  • Repair-turn structure: this harness's one-repair-attempt protocol with explicit error feedback may let the model self-correct order mistakes before they're ever recorded, which is consistent with 0% final old-form reversion despite the opportunity to slip.
  • Model: Experiment C's exact model is not confirmed to be the same gpt-6-luna used here.

Practical conclusion for the user's design question

Within this harness/model: reusing real Unix names with a documented grammar change was never worse than inventing new names, and performed identically to using Unix names with the correct grammar. The clear risk from this data is unfamiliar NAMES causing invalid_name errors, not grammar-order interference from familiar names. If forced to choose between "familiar name + non-standard args" and "fully novel name + same args," this experiment suggests the former is at least as safe, and likely preferable, for this harness/task family — the opposite conclusion from the user's stated hypothesis, though consistent with Study 1's own headline finding that invalid_name errors (not grammar misuse) drove the naming effect for shell.

Caveats

  • Single model (gpt-6-luna), single run per cell/seed combination (no bootstrap/CI), 24 tasks × 3 seeds = still a modest sample for Tier-3 (n=24 per condition).
  • Only one "near-miss" severity level tested (full 2-argument swap on 2 of 5 primitives) — Experiment C found effects scaled with how many rules changed; a milder single-flag-rename analog was not tested here.
  • old_form_grammar detection is a heuristic (based on whether the first positional arg looks path-like) — robust for this primitive set's args (patterns never start with /, paths always do, per vfs.py), but not a general-purpose grammar classifier.
  • Only the shell interface was tested (by design, since sequential/scripted showed no naming effect in Study 1) — it's possible a near-miss effect would surface differently in multi-turn tool-calling, where the model sees its own prior (correct) calls as few-shot context.
